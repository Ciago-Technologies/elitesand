# CiagoMem-SLAE R8 Remediation Verification (R9)

Input: `ciagomem-r8-fixed-review.zip` — the five-crate `ciagomem-slae/` workspace and the R8 master specification (648 lines). `New File/` and `review/` were treated as evidence only; nothing in the current source was overwritten. I read `README_UPLOAD.md`, `docs/R8_REMEDIATION.md` and `docs/VERIFICATION.md` first. Line numbers refer to the uploaded source unless marked "patched".

## 1. Verdict

The R8 fixes are applied as supplied, plus one useful hardening: the claim is now owned by a guard before fallible initialization, and zero/exhausted recovery counters are rejected. Every claimed test count reproduces. Outside `gclog.rs`, all changed core and engine files are byte-identical to my R8 patch.

The R8 review missed an older soundness defect that R8's new claim does not cover:

- **R9-1 (High, memory safety): a lifecycle or log can be dropped in safe Rust while the device still references its buffers.** Reproduced: a safe-code probe crashes with SIGSEGV in a normal release run, and Miri reports use-after-free in both the lifecycle and the log paths. R8's guard releases the core claim on that same drop, so a second log can bind while the first log's write is still in flight.
- **R9-2 (Low): the "exclusive publisher" claim is advisory.** Any code holding an arena can call `arena.core(0).unbind_log()` and `publish_durable(u64::MAX)`. The R8 ledger says these are trusted host operations, but the spec states exclusivity without qualification.

Both are fixed in the attached patch, with acceptance tests and Miri evidence. Production readiness and million-user capacity remain unverified.

## 4. Findings

### R9-1 High — safe drop with in-flight device I/O (use-after-free / DMA into freed memory)

Classification: confirmed defect. A safe-API soundness violation, demonstrated with the simulator (SIGSEGV and Miri). Behavior with the real `UringIo` backend is a plausible consequence, not executed here.

Location:
- `coagomem-core/src/io.rs` 63–67: the `IoBackend::write_at`/`read_at` safety contract requires the buffer to stay allocated until the CQE.
- `coagomem-core/src/lifecycle.rs` 241 and 544, 915: `SlotLifecycle` submits reads and writes into `arena.payload_ptr(idx)`. It has no `Drop`, and it only borrows the arena.
- `coagomem-core/src/slot.rs` 735–746: `SlotArena::drop` frees or unmaps the payload memory unconditionally.
- `coagomem-wal/src/gclog.rs` 686–687: the SAFETY comment says "It is not freed before the log is quiescent". Nothing enforces this: dropping `GroupCommitLog` frees `bufs` immediately. The R8 `LogBinding` drop (276–279) also releases the core claim at that moment.

Why it is a defect: `admit_load`, `poll` and `on_cqe` are safe functions that discharge an `unsafe` precondition. Safe code can then drop the lifecycle and arena, or the log, before the CQE, which the R8 ledger acknowledges ("drain/cancel outstanding I/O before destroying a log"). A documented obligation cannot make a safe API sound. This path is ordinary in practice: panic unwinding, error returns during startup, or shutdown drop these values with I/O outstanding. With `io_uring`, a read completing into freed memory corrupts whatever the allocator reused it for. A write reading freed memory can persist unrelated process data to the log device.

Reproduction (upload):
- `tests/r9_review.rs` → `defect_r9_1_lifecycle_drop_with_inflight_read`: release run crashes with signal 11 (SIGSEGV); Miri reports "alloc… has been freed, so this pointer is dangling".
- `coagomem-wal/tests/r9_review.rs` → `defect_r9_1_log_drop_with_inflight_write`: release run shows a second `open` on the same core succeeding while the first log's write is in flight; Miri reports "dangling reference (use-after-free)" at the completion.

Smallest compatible fix (patched):
- `slot.rs` 413, 793–815: `SlotArena` gets an `io_pending: AtomicU64`, maintained by the lifecycle at submit and completion. `Drop` leaks the backing memory while `io_pending > 0` instead of freeing it. Leaking is the only sound option when no completion can be awaited.
- `lifecycle.rs` 266–297 (patched): `impl Drop for SlotLifecycle` fences the core if any load or checkpoint is outstanding, so late DMA cannot be served as valid data. New `quiescent()` accessor and `unsafe fn release_device_references` (279–297); submit and completion paths update the arena counter.
- `gclog.rs` 306–316: `impl Drop for GroupCommitLog`, if not quiescent, fences the core and `mem::forget`s the buffers. The claim is still released, but the fence makes `open` on those controls refuse, so fresh controls are required.
- `GroupCommitLog` gets a matching `unsafe fn release_device_references(&mut self)` for hosts that have destroyed or reaped the ring. In-tree caller changes: the WAL crash-cycle test calls it after `SimIo::power_loss`, and the two core lifecycle unit tests that end with simulated I/O still outstanding (`slot_is_freed_only_after_its_checkpoint_cqe` at patched line 1340, `randomized_interleavings_never_lose_or_mix_state` at 1629) call the lifecycle version. Without that call, Miri correctly reported those two tests as leaking the arena; this is the fail-safe leak working as designed, not a defect.

No format or dependency change; one 8-byte field per arena (not per slot).

Acceptance:
- `tests/r9_regressions.rs` → `r9_1_lifecycle_drop_with_inflight_read_fences_and_arena_memory_survives`, `r9_1_completed_io_returns_arena_to_zero_pending`, `r9_1_released_lifecycle_neither_fences_nor_leaks`.
- `coagomem-wal/tests/r9_recovery.rs` → `r9_1_dropping_log_with_inflight_write_fences_and_keeps_buffer_live`, `r9_1_quiescent_drop_still_releases_cleanly`.
- All pass in release mode and under Miri.

Residual and exit criteria: leaking is bounded per abandoned log (`buffers × buf_bytes`) or arena. A host that forgets a lifecycle with `mem::forget` skips the fence, but the arena still leaks rather than frees, so memory safety holds. A second lifecycle created over a range whose previous owner was dropped mid-I/O can still receive a late DMA; the fence prevents serving it. The production fix is a reactor that owns both the ring and the buffers and cancels and reaps every operation before teardown, plus a real-`io_uring` teardown test.

### R9-2 Low — publisher exclusivity is advisory

Classification: confirmed design gap. It requires host code to misuse a public API, and the R8 ledger declares those calls "trusted"; the spec claim is unqualified.

Location: `slot.rs` 254 (`pub fn publish_durable`), 268 (`pub fn bind_log`), 274 (`pub fn unbind_log`), 501 (`SlotArena::core` returns `&CoreControl` to any arena holder). Spec line 37.

Reproduction (upload, PASS): `coagomem-wal/tests/r9_review.rs` → `defect_r9_2_arena_holder_bypasses_publisher_claim`. An arena holder unbinds a live log's claim, a second log opens, `publish_durable(u64::MAX)` succeeds, and an unwritten slot passes a `Durable` read.

Smallest fix (patched `slot.rs` 255–340): `publish_durable`, `bind_log` and `unbind_log` become `pub(crate)`. A new `coagomem_core::slot::DurabilityPublisher` is created only by a successful `claim(controls, core)`, publishes through `publish(lsn)`, and releases the claim in `Drop`. A refused claim constructs nothing, so it cannot release someone else's claim. `GroupCommitLog` holds a `DurabilityPublisher` in place of `LogBinding`. Read-only `CoreControl::log_bound()` is added. `lib.rs` is untouched, so the embedded spec listing still validates. Three tests that published directly now claim a publisher.

Acceptance:
- `coagomem-wal/tests/r9_recovery.rs` → `r9_2_no_second_publisher_while_a_log_is_bound`, which includes the check that a refused claim keeps the existing claim.
- `tests/r8_regressions.rs` → updated `r8_1_core_control_layout_and_single_publisher_claim`.
- Two `compile_fail` doctests on `DurabilityPublisher`: `arena.core(0).publish_durable(..)` and `c[0].unbind_log()` no longer compile.

`fence()` stays public because fencing fails safe.

## 5. Tested behavior vs. missing production integration

Tested at component level:
- exclusive per-core publication;
- rejection of stale and shorter recovery;
- teardown that cannot free memory under in-flight I/O;
- export freshness;
- the engine is `Send + Sync`;
- pin retention, exact clean loads and the monotonic replay clock (R7).

Missing, so none of this is end-to-end:
- **Durability:** the engine's `Journal` has only `MemoryJournal` (no `GroupCommitLog`-backed journal exists), so engine operations are not durable.
- **Startup and recovery:** there is no node or reactor constructor that allocates controls, opens one log per core and validates every arena, no ring-owning teardown with cancel/reap, no WAL replay or repair driver, and no durable checkpoint catalog (image epoch included).
- **Security:** the production identity anchor and transport authentication are absent.
- **Storage and capacity:** storage qualification has not been done. The only memory figures backed by evidence are 33 B/slot dirty tracking, 256 B per core and 8 B per arena; no RSS, latency or user-count claim follows.

## 7. Exact specification corrections

Line 37, replace "Logs claim their core's publisher role exclusively; duplicate binding and shorter-than-published recovery reject. A private binding guard releases the claim on normal drop and failed initialization." with:

> Durable publication requires a `DurabilityPublisher`, of which at most one exists per core; `publish_durable`/bind/unbind are crate-private. Logs hold that publisher; duplicate binding and shorter-than-published recovery reject. The publisher releases its claim on drop and failed initialization. Dropping a log or lifecycle with device I/O outstanding fences the core and leaks, rather than frees, the referenced buffers.

Line 170, replace "WAL open binds the array/core ID and claims the single log-publisher role until its binding guard is dropped." with:

> WAL open binds the array/core ID and holds the core's only `DurabilityPublisher` until the log is dropped; no other code path can advance the watermark.

Line 170, append after "Stale/duplicate lifecycle CQEs are rejected before decrementing in-flight counts.":

> Buffers referenced by submitted I/O are never freed by safe code: a non-quiescent `GroupCommitLog` or `SlotLifecycle` drop fences the core, and `SlotArena` leaks its backing while `io_pending > 0`. A production reactor must cancel and reap all operations before teardown; `release_device_references` is the unsafe acknowledgement that it has done so.

Line 157, append:

> The `IoBackend` buffer-lifetime contract is upheld by the owning types' destructors, not by caller discipline.

Line 622, replace the "Current disposition" cell with:

> R9 reviewer ran Miri on the R9 core/WAL acceptance tests, the R8/R7 WAL recovery tests and the full `coagomem-core` library after the R9 patch (results in the R9 report), plus an aarch64 compile check. Engine Miri, loom/Shuttle, real `io_uring` teardown and ARM execution remain open.

## 8. Full-library Miri and ARM compile

- Full `coagomem-core` library under Miri, without `-Zmiri-ignore-leaks`, after the patch: 18 passed, 0 failed, no undefined behavior, no leak reports, 759.5 s (`logs/r9_miri_corelib.log`). This covers the envelope, lifecycle, mesh, seqlock and slot unit tests, including the randomized lifecycle interleavings.
- Why leak suppression appears elsewhere: the R9-1 acceptance tests deliberately drop owners mid-I/O, and the correct result is a leak. Those runs use `-Zmiri-ignore-leaks` only to allow that; they still check for UB. The full-library run shows that ordinary quiescent teardown does not leak.
- `cargo check --target aarch64-unknown-linux-gnu --workspace --all-features` on the patched tree: exit 0 (`logs/r9_arm.log`). The tests were compiled, not run, so ARM memory-ordering behavior is not established ([Rust atomics](https://doc.rust-lang.org/std/sync/atomic/index.html)).
