## Breaking API changes and restore rules

Arena constructors take shared controls rather than a core count. Capabilities require BootEpoch; RequestCtx must receive the current trusted engine epoch. Provenance/approval signature framing advances to v3 and includes that epoch; old signatures cannot authenticate through the new API. Label::attested and NonceTracker constructors require the new scope/budget inputs. Load admission takes RecoveryBounds and distinguishes Absent, ReplayRequired and NeedsRepair. No automatic compatibility shim bypasses these checks.

The identity journal format already stored the full incarnation and remains readable. Existing incarnations survive normal lookup/restart; only a new create draws new entropy. Keep the independently durable anchor outside the restored data failure domain. After restore/start, generate a new SessionEpoch and obtain fresh capabilities/provenance/approvals; do not persist fixture boot IDs. Full VM restore needs a validated guest RNG reseed/VM-generation protocol. A production anchor and restore drill remain open.

## Memory and evidence

On the tested x86_64 build: Label=176 bytes plus up to 64 bytes of reader payload and allocator overhead; FrameValue=320; SlotHeader=128; CoreControl=256. One shared 14-core control array is 3,584 bytes before Arc overhead. Dirty arrays now include a one-byte barrier flag, **33 bytes per slot**, or 31.47 MiB for a million owner-partitioned slots. The replay tracker is bounded by configured active tenants times per-tenant quota, with hash/heap allocation overhead that must be charged by the host. No million-user capacity claim follows from this arithmetic.
